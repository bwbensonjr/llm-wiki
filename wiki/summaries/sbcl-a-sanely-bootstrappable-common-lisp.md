# SBCL: A Sanely-Bootstrappable Common Lisp

## Summary

Christophe Rhodes's 2008 paper (Self-Sustaining Systems workshop) on how Steel Bank Common Lisp builds itself. It opens with a distinction between **image-oriented** development, where the unit of interchange is a memory dump of every object in the system, and **source-oriented** development from files run through `compile-file`. Common Lisp application programmers mostly work from source, and keep image saving, which is outside the standard, chiefly "as a deployment strategy". They also periodically confirm that their sources still compile from scratch, because nothing guarantees an image's state is reproducible from its sources. Lisp *implementations*, Rhodes notes, are the reverse: most Lisp-written Lisps build by taking an earlier version of themselves and mutating it until it can compile the new sources, then dumping an image, with mutations that differ per change and can be very involved.

SBCL, a 1999 fork of CMU Common Lisp, is about 90% Lisp (roughly 250,000 lines) plus C and assembly for signal handling, platform code and an 8,000-line garbage collector kept in C so it can be debugged with gdb. Its build is reproducible from **any** conforming Common Lisp. The host compiles SBCL's sources into a cross-compiler running inside it; C headers describing Lisp object layouts are generated by introspection; the C runtime is built; the cross-compiler compiles the sources again into FASL files; and a *genesis* program pseudo-loads those FASLs into byte vectors representing the target's memory, writing a "cold core". Top-level forms cannot run during genesis, so they are deferred to a **cold init** phase when the runtime boots that core. Rhodes calls it the most fragile part of the build and the hardest to debug, since there is no Lisp debugger yet. After cold init, packages are renamed, CLOS (derived from PCL) is loaded, and the final `sbcl.core` image is saved.

Host and target are kept apart by naming: target packages are `sb!`-prefixed during the build, target feature tests use `#!+`/`#!-`, and a shadow package `sb!xc` holds target versions of operators such as `defconstant` and `defmacro` that must not overwrite the host's. `eval-when` needs particular care: a `:compile-toplevel` definition must use the host's `defun`, while the `:load-toplevel` part must be compiled with the cross-compiler's. The payoff is that contributors need not understand the bootstrap; a CMUCL fix that needed hand-written bootfiles and two builds was an ordinary source change in SBCL. The cost is that the compiler is built twice, and CLOS's metacircularity keeps it out of the cross-compiler.

## Why this matters

The paper shows how deeply the image is woven into Lisp delivery: even a Lisp that builds reproducibly from source ends by dumping a heap, and the part that resists separate compilation most, running top-level forms in the right order, is exactly what has to be deferred to cold init. Its host and target separation, with `eval-when`'s compile-time versus load-time split, is a working instance of the phase problem [[composable-and-compilable-macros|Flatt]] describes. That makes it relevant to [[separate-compilation]] and standalone delivery in any Lisp that compiles itself, alongside [[clasp|Clasp's]] multi-stage bootstrap.
